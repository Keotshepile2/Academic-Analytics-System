APA-DSS
Academic Performance Analytics & Decision Support System

A web-based analytics platform that reads from the existing Student Record Management System in read-only mode and provides interactive dashboards, academic KPIs, and an interpretable machine-learning model for early at-risk student identification.

🎓 Author: Keotshepile Keikabile 🏛 Institution: Sol Plaatje University 📅 Year: 2026 💻 Stack: Node.js · MySQL · Python
01 — The Problem

Why this project exists

Student Record Management Systems (SRMS) are excellent at storing academic information — marks, modules, enrolments, and progression. However, they are rarely designed to analyse it.

Lecturers, programme coordinators, and academic advisors must currently extract data manually, build their own spreadsheets, and interpret results without any consistent methodology. By the time a struggling student is identified, the semester is often already lost.

APA-DSS does not replace the existing SRMS. Instead, it connects to the existing database in read-only mode and transforms academic records into understandable performance indicators, trends, and decision-support information — including an interpretable machine-learning model for early at-risk detection.
02 — Project Objectives

What APA-DSS sets out to accomplish

  • Analyse the existing student records without modifying the source SRMS database.
  • Calculate academic KPIs — pass rates, average marks, GPA trends, progression rates.
  • Identify performance trends across semesters, programmes, faculties, and modules.
  • Analyse module and programme performance to surface failure hotspots.
  • Identify potentially at-risk students using a machine-learning classifier.
  • Provide interpretable ML predictions with plain-language risk factors.
  • Generate reports with CSV export and print/PDF support.
03 — Core Features

What the system delivers

📊 Dashboard

Six headline KPIs (students, programmes, modules, pass rate, average mark, at-risk count), a GPA trend line chart, academic progression breakdown (Proceed / Repeat / At-Risk / Excluded), Top-5 and Bottom-5 modules by pass rate, a failure-hotspots bubble chart, and at-risk alerts by programme. All with semester, faculty, and programme filters.

👨‍🎓 Student Analytics

Searchable, sortable table with multi-filter support. Each student opens a drill-down modal with a colour-coded risk banner, class rank within programme, marks history chart, comparison to programme and university averages, and a failed-modules list.

📚 Module Analytics

Module performance table with pass rate, average mark, and a difficulty index. Each module opens a detail modal with rank within programme, pass-rate trend, mark distribution histogram, and the bottom-5 performing students.

🎓 Programmes & Faculties

Programme and faculty cards with key metrics and comparison modals.

⚠️ At-Risk Students (Machine Learning)

Logistic Regression classifier trained with scikit-learn. Includes a Model Card, a risk distribution histogram across all scored students, per-student top risk factors in plain language, and a retrain button that triggers the full ML pipeline end-to-end.

📄 Reports

Academic Summary, Module, Programme, Student, and At-Risk reports — exportable as CSV or printable as PDF through the browser.

04 — System Architecture

How the system fits together

APA-DSS follows a layered, read-only architecture that integrates with the existing SRMS without modifying it.

Presentation Layer
Web Browser — HTML5 · CSS3 · JavaScript · Chart.js
Dashboards · Tables · Filters · Reports
▼ HTTPS / JSON
Application Layer
Node.js 18 + Express 4
Auth Routes · Analytics API (/api/apa-dss/*) · Session Management
▼ SELECT only
▼ child_process
Data Layer
MySQL 8 — student_record_system
🟢 apa_dss_user · GRANT SELECT only
ML Layer
Python 3.11
scikit-learn · pandas · joblib · Logistic Regression

Key architectural decisions

DecisionReason
Read-only DB userProtects the existing SRMS from accidental modification.
Separate apa_dss_userPrinciple of least privilege — analytics never has write access.
Python via child_processKeeps ML logic in its native ecosystem without a separate microservice.
Session-based authMatches existing SMS admin model — no duplicate user store.
Chart.jsLightweight, no build step, framework-agnostic.
05 — Database Integration

Where the data comes from

APA-DSS reads from the existing student_record_system MySQL database — the same database used by the Student Record Management System. It never writes to it.

Tables used (read-only)

TablePurpose
studentsStudent identity, programme, year enrolled, status
modulesModule code, name, credit hours, year level, semester
student_enrollmentsLinks students to modules, records marks and grades
programmesProgramme metadata linked to faculties
facultiesFaculty metadata
semestersAcademic year and semester definitions
adminsAdministrator login credentials (used for APA-DSS auth)

Read-only database user

A dedicated apa_dss_user was created with the minimum privileges required:

CREATE USER 'apa_dss_user'@'localhost'
  IDENTIFIED WITH mysql_native_password BY '••••••';
GRANT SELECT ON student_record_system.* TO 'apa_dss_user'@'localhost';
FLUSH PRIVILEGES;

07 — Machine Learning

Early At-Risk Student Identification

Algorithm: Logistic Regression

Logistic Regression was chosen because it is interpretable, fast, and produces well-calibrated probabilities — all critical for a decision-support tool that must be explainable to academic staff.

At-Risk Definition

A student is classified as At-Risk if they failed ≥ 50% of the modules they attempted in their most recently completed semester.

This definition is evidence-based, actionable, and avoids data leakage (it uses only past performance, never future outcomes).

09 — Limitations

What APA-DSS does not claim

  • 🔒 Local database. MySQL runs on the developer's machine. The web app cannot reach it from another computer without a hosted backend.
  • 🧪 Synthetic training data. ML metrics validate the implementation, not real-world prediction quality.
  • 🤝 Decision support only. APA-DSS assists academic staff — it does not replace human judgement.
  • 🏛 Not deployed institutionally. Production deployment would require hosted DB, HTTPS, hardened auth, audit logging, and POPIA compliance review.
  • 📊 No real institutional validation. Real historical data would be needed to confirm usefulness.
